# 学习中心下一轮优化建议（2026-07-22）

> 状态：第二阶段已实施（2026-07-22）
>
> 已落实：自动保存与本地草稿恢复、主进程全文检索与命中摘要、收件箱/待整理筛选、Browser AI 任务结果的结构化学习笔记沉淀与保存前编辑预览、`[[笔记标题]]` 关联/反向引用、轻量今日回顾。模板与数据导入导出仍按本文推荐顺序留待后续阶段。
>
> 范围：基于当前已实现的笔记、Skills、浏览器 AI 任务能力做的产品与架构评估。

## 结论

学习中心的基础工作台已经成型：笔记支持分类、标签、草稿/已整理状态、Markdown 编辑与预览；Skills 和浏览器 AI 任务也已经是独立视图。下一轮不宜继续把重心放在三栏布局或增加按钮，而应让内容完成一条可重复的闭环：**记录 → 找到 → 整理 → 复习/复用 → 沉淀 AI 结果**。

建议优先推进下面四项：

1. 全文检索与结果定位；
2. 自动保存、离开保护和可恢复草稿；
3. 面向学习的待整理、复习和关联能力；
4. 浏览器 AI 结果的一键结构化沉淀。

前三项直接改善笔记的日常可用性；第四项才能让已有的浏览器 AI 任务不止停留在“查看历史”。

## 当前基线与已经解决的问题

当前实现已经覆盖了此前 UI 提案中的大量内容，因此不建议重复做同类改动：

- `LearningCenterHeader` 已提供 Notes、Skills、浏览器任务三种视图，并在窄窗口用 Select 保持可达。
- `LearningEditorPanel` 已支持标题直接编辑、编辑/分栏/预览、保存状态、侧栏收起和无选中笔记时的可执行空态。
- `LearningNotesSidebar` 已有标题与摘要搜索、分类筛选和按需展开的分类管理。
- `LearningNoteInfoSidebar` 已展示分类、标签、状态、日期和保存情况。
- 浏览器 AI 历史已经能筛选、查看回答与来源、重开任务、复制回答、另存为笔记或追加到当前笔记。

也就是说，下一轮的判断标准应从“能否完成 CRUD”升级为“内容量增长后，用户还能否低成本地找回、整理并复用知识”。

## 优先级建议

| 优先级 | 优化项 | 用户价值 | 主要改动层级 |
| --- | --- | --- | --- |
| P0 | 笔记全文检索与命中定位 | 内容不再只能靠标题/120 字摘要找回 | shared → main learning → IPC/preload → store/UI |
| P0 | 自动保存与草稿恢复 | 降低丢内容风险，减少手动保存负担 | renderer；恢复草稿时扩展本地持久化 |
| P1 | 收件箱、待整理与复习队列 | 让“draft/organized”成为真正的学习流程 | shared → main → IPC/preload → store/UI |
| P1 | 笔记关联与反向链接 | 将散落笔记组织成知识网络 | renderer 起步；稳定后扩展索引 |
| P1 | AI 结果结构化沉淀 | 把回答转为可编辑、可追溯的学习材料 | renderer，必要时扩展 note 元数据 |
| P2 | 模板、快速捕获和每日回顾 | 缩短记录与复习的启动时间 | renderer + i18n |
| P2 | 数据可携带性与备份 | 本地知识可导出、迁移、恢复 | main learning + IPC/preload |

## P0：让“找得到”和“不会丢”成为默认体验

### 1. 全文检索，而不是只搜索摘要

现有笔记列表的搜索在 renderer 中针对 `LearningNoteSummary` 过滤。摘要来自 Markdown 的前 120 个字符，因此正文中段的概念、代码片段和结论无法被检索到；笔记积累后会成为最明显的效率瓶颈。

建议：

- 搜索框保留即时筛选体验，但将输入经 150–250 ms 防抖后发到 learning domain。
- 搜索范围至少包括标题、标签和完整 `contentMd`；结果返回命中位置和一小段上下文，而不把所有正文一次传回 renderer。
- 结果按标题命中、标签命中、正文命中和更新时间排序；界面显示命中摘要，并在打开笔记时定位/高亮首个命中。
- P0 不需要引入第三方全文检索库。现有 Markdown 文件规模较小时可由主进程顺序读取并限制返回数量；当数据量或延迟达到阈值，再增加本地倒排索引。

建议契约：

```ts
type LearningSearchResult = LearningNoteSummary & {
  matchKind: 'title' | 'tag' | 'content'
  matchExcerpt: string
  matchOffset?: number
}
```

落点遵循既有链路：`shared types → main/learning service + repository → IPC handler → preload invoke API → appStore learning slice → LearningNotesSidebar`。不要让 renderer 自行读取全部笔记文件。

验收：用一段不在标题和摘要首段的文字可以找到目标笔记；无结果、加载中、检索失败各有明确反馈；搜索不阻塞输入或编辑。

### 2. 自动保存、离开保护与可恢复草稿

当前有保存状态、`Ctrl/Cmd + S` 和显式保存，但长文写作仍依赖用户主动保存。窗口关闭、切换笔记、切换视图或写到一半发生异常时，风险仍然存在。

建议分两层实施：

1. **自动保存**：内容停止输入约 800–1200 ms 后保存；编辑期间显示“正在保存”，失败后保留修改并提供重试。显式保存与快捷键仍保留，立即 flush 当前变更。
2. **恢复草稿**：在真正写入笔记前或写入失败时，把当前编辑快照存进受控的 renderer 本地存储；下次打开同一笔记时，若草稿更新于正式笔记，提示“恢复草稿 / 丢弃草稿 / 查看差异”。

实现约束：

- 为每个 `noteId` 维护一个保存版本或递增序号，忽略旧请求晚返回造成的回写；切换笔记和卸载时取消 debounce，并只 flush 当前最新版本。
- 先实现单设备、本地恢复，不做多窗口或云端同步。若日后需要冲突处理，再在 shared 模型增加 revision 字段。
- 删除笔记时一并清除其本地草稿；删除前确认语义保持不变。

验收：连续输入后无需额外操作即可保存；保存失败不覆盖本地编辑值；重新进入页面能够恢复未落盘的草稿，且用户可以拒绝恢复。

## P1：把“笔记”变成学习系统，而不是文件列表

### 3. 收件箱、待整理和复习队列

现有状态只有 `draft | organized`，但左侧栏无法直接按状态浏览，也没有提醒用户哪些内容需要继续处理。这使状态仅是信息字段，而没有驱动行为。

建议：

- 在笔记筛选中增加固定入口：全部、收件箱（未分类或 draft）、待整理、最近修改、已收藏；保留分类与标签作为二级过滤。
- 第一阶段不必改动存储：`未分类 || draft` 可以由当前字段推导。随后再评估是否引入 `pinned`、`reviewAt`、`reviewIntervalDays` 等明确元数据。
- 增加“今日回顾”轻量入口：默认给出到期/长期未访问的少量笔记，支持标记“已回顾、明天再看、暂停”。
- 不建议一开始做复杂的间隔重复算法；先采用手动或固定间隔，验证用户是否真的使用复习队列。

验收：用户能在一次点击内找到所有未整理笔记；回顾操作不会改写正文；没有待回顾内容时显示下一次可执行操作，而非空白列表。

### 4. 笔记关联、链接和反向链接

分类适合稳定的层级，但不足以表达“这条结论来自哪次调研”“这段知识和哪个 Skill 有关”。建议支持 Markdown 内的笔记链接，例如 `[[笔记标题]]`，并提供：

- 输入 `[[` 时的标题搜索与补全；
- 打开笔记时显示其引用的笔记和“被哪些笔记引用”；
- 删除或重命名笔记时提示引用影响，但不要自动批量改写正文；
- 在右侧信息栏先以只读关联区呈现，避免把编辑区变成管理表单。

第一版可由 renderer 在当前笔记正文中解析正向链接，并在打开详情时按需扫描索引中的候选内容。反向链接和重命名安全性稳定后，再由 repository 维护单独索引。

验收：用户能从一条笔记跳转到相关笔记并返回；不存在的链接有可辨识的无效状态；不会因链接解析影响普通 Markdown 预览。

### 5. AI 结果以“可学习材料”沉淀，而不是整段粘贴

现有浏览器 AI 任务已能另存回答和追加回答，基础闭环不错；但长回答直接进入笔记会带来格式混乱、来源不清和后续难复习的问题。

建议在任务详情中增加“沉淀为学习笔记”操作，提供一个小型预览/编辑步骤：

- 默认生成标题、结论、关键要点、待验证问题、来源任务链接等 Markdown 结构；
- 允许选择“新建笔记”“追加到当前笔记”“仅复制”；
- 明确保留来源站点、任务时间、所选上下文的摘要，不默认把敏感来源正文重复写进笔记；
- 对原始回答提供折叠区或链接入口，避免同时出现两份大段正文。

这项能力首先可在 renderer 侧把已有任务记录转换为 Markdown。只有在需要稳定追踪来源、统计引用或迁移数据时，再将 `sourceTaskRecordId` 加入笔记 frontmatter 和 shared 类型。

验收：从任务记录创建的笔记在脱离历史记录后仍能读懂结论与基本来源；用户能在保存前修改生成内容；敏感来源不会被静默复制。

## P2：降低记录和维护成本

### 6. 模板、快速捕获和每日入口

默认新建笔记只有通用列表骨架。建议把重复结构变成可选择的本地模板：课程笔记、问题拆解、阅读摘录、项目复盘、AI 回答沉淀。模板只提供初始正文与推荐标签，不自动创建分类。

另可在 Home 或全局命令入口加“快速捕获”：只输入一句话即可进入收件箱，后续再完善。每日回顾可显示近期草稿、待复习笔记和最近 AI 任务三项，控制在一屏内。

### 7. 导出、导入与备份可见性

笔记目前是用户数据目录下的 Markdown 与 JSON 索引，天然适合可携带性，但用户无法从产品中确认位置或执行备份。

建议提供：

- 打开学习数据目录；
- 导出选中/全部笔记为 Markdown 包，分类和元数据一并保存；
- 导入前预览冲突，并提供“跳过、复制为新笔记、覆盖（需确认）”；
- 在设置中显示最近备份时间与恢复说明。

这是主进程文件能力，应独立为 learning domain 的导入导出 API；不要让 renderer 获取任意文件系统路径。

## 推荐实施顺序

1. **自动保存与恢复草稿**：投入小、可单独验证、直接降低风险。
2. **全文检索**：建立“笔记变多仍可用”的基础；先不引入索引依赖。
3. **状态筛选与收件箱**：复用已有 `draft/organized/categoryId`，最快形成整理流程。
4. **AI 结果结构化沉淀**：在现有任务历史的基础上提高复用价值。
5. **笔记关联与复习队列**：等前三项稳定、内容样本足够后再决定具体字段与交互。
6. **导入导出**：在数据模型趋稳后完成，减少格式反复迁移。

## 不建议当前投入的方向

- **再做一轮纯视觉重排**：现有三栏、响应式视图切换和编辑模式已覆盖主要骨架问题，应先用真实内容验证而不是反复调布局。
- **把 Skills 与笔记强行合并成一套数据模型**：两者用途不同；保持独立实体，只通过链接、标签或 AI 任务来源建立关联。
- **一开始引入向量数据库、云同步或复杂间隔重复算法**：这些会显著扩大隐私、冲突处理和维护成本。应先确认本地检索、草稿恢复和基础回顾是否被持续使用。
- **自动把全部笔记送给浏览器 AI**：现有“显式选择来源”的隐私边界正确，应继续保持。

## 评审时需要确认的决策

1. 自动保存是默认开启，还是需要设置项？建议默认开启，并保留关闭开关给有特殊工作流的用户。
2. 全文检索是否允许检索 Browser AI 保存的原始上下文？建议默认只检索学习笔记与用户明确保存的任务内容，敏感来源维持排除。
3. “复习”是轻量待办，还是要做正式间隔重复？建议先做前者。
4. AI 结果沉淀是否要记录可追溯来源？建议记录任务 ID、站点和时间，但不默认复制敏感原文。

## 完成标准

- 写作中无需反复手动保存，异常或切换后可恢复近期草稿。
- 用户能用正文中的关键词在合理时间内定位笔记，并看到命中上下文。
- 未分类/未整理内容有明确入口，用户知道下一步该处理什么。
- AI 任务的有效结论可被沉淀为可编辑、可追溯的笔记，而非一次性历史记录。
- 所有新增可见文案接入 `learning` messages；涉及数据能力的改动完整遵循 shared → main → IPC → preload → store → renderer 链路。
